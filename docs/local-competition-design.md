# 架空ローカル大会の追加設計

調査対象：HEAD `cc3cdb5` の `model.ts`、`careerTypes.ts`、`competitions.ts`、`progress.ts`、`simulation.ts`、`storage.ts`、`validation.ts`、`validateProgress.ts` と大会・保存テスト。2026-11-19作成。外部資料は使用しない。ここで提案する大会名・日程・資格・費用・採点・CPUはすべてゲーム独自。既存公式参照8大会・結果・資格・世界タイトルは維持する。

## 最小影響の構造

`Career.local?: LocalCompetitionState` を推奨する。`experience` は競技経験の集計にも使いたくなる曖昧な名前なので、独立した機能を表す `local` の方がよい。既存 `CareerProgress` の `Series`（公式8種）、`Circuit`（jbbf/npc）、`Result`、`Credential`、`Title` に架空大会を追加しない。

```ts
type LocalSeries = 'gymMeet' | 'rookieMeet' | 'localOpen';
type LocalClass = 'Open' | 'under70' | 'under85' | 'over85';
type LocalParticipantId = 'player' | `local-cpu-${string}`;
interface LocalCompetitionState {
  version: 1;
  rulesVersion: 'local-fiction-1';
  seed: number;                   // 専用乱数の基点。profileIdに依存しない
  anchorDay: number;              // 新規は0、旧キャリア導入時はその当日
  lastUpdateDay: number;
  goalEditionId: string | null;
  decision: LocalDecision | null;
  entries: LocalEntry[];
  results: LocalResult[];
  rivals: LocalRival[];
}
```

`LocalEntry` は `editionId,series,showDay,deadlineDay,status,paidFee,paidTravel,checkInWeight,classId,rulesVersion` を保持。状態は `entered → checkedIn → completed` と `withdrawn/missed`。申込済みの開催は再申込不可。`LocalResult` は `id,entryId,editionId,day,series,category,experienceClass,weightClass,rank,count,score,body,posing,appearance,standings,comparisonToPrevious,rulesVersion`。出場前の状態と採点内訳を凍結して保存する。

`LocalRival` は身体・能力上限・posing・左右差・疲労・前夜睡眠・全身疲労・成長係数・開始日・更新日・大会履歴を持つ。審査用入力にプレイヤーと同じ項目が必要。過去結果は現在CPUを参照せず、結果内のスナップショットから再表示する。

**入れ子のプレイヤーIDは `'player'` にする**。現在の `importSave` は新しいathlete.idへ変更し、既存officialのpodium内だけ旧IDを置換している。localでも生のathlete.idを大量に保存すると移行漏れを起こす。画面上で `'player'` をそのキャリアの選手名へ解決すれば、インポートでNPCとの区別が壊れない。

## 開催コンテンツ案

開始日はday0。day13は開始14日目、つまり2週目の終わり。旧キャリアは保存済み `anchorDay` から数え、過去の大会を後付けしない。新規キャリアでは3大会を最初から見られ、どれでも条件を満たせば申請できる。目標提案は参加・準備・自己ベストを中心にし、勝利を次の大会の解放条件にしない。

| 架空大会 | 初回／以後の周期 | 締切（当日を含む） | 費用／移動／拘束時間 | 部門・区分 |
| --- | --- | --- | --- | --- |
| リーフジム・ミニコンテスト | anchor+13、14日ごと | 開催2日前まで | 500円／0円／2時間 | 成人男子ボディビル練習会、体重無差別、経験制限なし。比較＋短いポーズ体験 |
| みどり地域・新人ステージ | anchor+20、28日ごと | 開催4日前まで | 1,500円／500円／4時間 | 成人男子新人ボディビル。下記の参加経験条件。70kg以下、70超85以下、85超 |
| 川沿い地方・オープンカップ | anchor+34、56日ごと | 開催7日前まで | 4,000円／2,000円／6時間 | 成人男子ボディビル、経験制限なし。新人と同じ体重区分 |

この位相だと3大会同士は同日にならない。日付は架空カレンダーの確定値として保存する。申込から最低2日の準備期間を確保し、過ぎた開催へ申込不可。今季見送り・欠場から次の開催は常に表示する。初回ジム大会を見逃しても2週間後に再挑戦できる。大会のたびに月額会員費を追加したり、登録料・移動費を二重徴収しない。賞金・勝利による身体強化は初版では不要。

初回の目標文例：`14日目の練習会で、今の身体とポーズを記録する`。次の目標は `前回からポージングを1項目改善`、`大会前日の休養を予定に収める`、`前回の自分の採点を超える`。改善量を満たしたら必ず勝てるとは表示しない。

## 新人条件と階級

新人ステージの初版条件案：**過去に出場完了したボディビル大会が5回未満**。参加数はlocal新人・localOpenと既存official8大会の完了結果を数える。練習会は体験会なので除外。申込・欠場・missedは参加数に含めない。優勝回数・順位で卒業させない。5回目の出場は可能、6回目はOpenか練習会を提案する。正式プロ資格保有者は新人区分対象外（練習会／localOpenはこの架空ルールでは参加可能だが、実在団体への参加許可とは無関係）。参加経験による卒業とプロ除外を別理由で説明する。

初版は「通算参加経験」で明示する。年度が変わってゼロへ戻さない。表示は `対象大会の参加経験 2/5回`。同一大会二重結果は数えず、結果IDではなくentryId単位でも一意性を検証する。現在の公式 `Result` は成人シニア男子だけなので、将来他部門を追加した場合にもカテゴリーの明示フィルターを残す。

新人資格は**申込時に仮確認し、チェックイン時にも再確認**。複数開催を同時申込して上限を越える場合、対象外となった未開催新人エントリーは申込費・未使用移動費を自動返金して取消し、理由と次のOpen開催を表示する。隠れた強制失格・資金損失を避ける。初期実装を簡素にするなら未完了ローカル申込は1件に制限し、その制限を画面に表示する。

体重区分は当日のチェックイン体重で固定。3人未満の区分は事前に定義した隣接階級と統合し、変更前後と参加数を表示。統合順は軽量→中量、重量→中量、中量不足→参加者が多い側（同数なら軽量側）。全体でも3人未満なら順位競技を開催せず、無料の非順位の測定・ポーズ記録へ切り替え、参加費・移動費を返金。新人参加回数も進めない。プレイヤーだけの自動優勝を作らない。

## 固定CPUの生成と変化

初回導入時に専用seedから64人程度を生成して保存する。既存officialの128人は高い技術と低脂肪が中心なので、単にtierを下げて流用しない。新規の架空選手は定数の体格分布から作り、プレイヤーの現在身体、profileId、敗北数、予算、周回数を一切読まない。大会レベルも保存した定数。

| 層 | 身体・技術の内容例 | 固定選手例（仮名） |
| --- | --- | --- |
| 練習会 | 体重55〜105kg、体脂肪12〜30%、posing0.03〜0.35。筋量の少ない人・技術が未熟な人・バランス良好な人を混在 | 白井航：ポーズ初心者／森田悠：脚が得意／木下誠：継続が得意 |
| 新人 | 同じ体重帯に分散、posing0.12〜0.55、部位の偏り・調整経験の違い。初心者に勝利を保証する能力上限を設けない | 田辺涼：仕上がり安定／高井陸：上半身に厚み／小西蓮：技術を伸ばす |
| 地方Open | posing0.30〜0.80、筋量・バランス・調整に広い差。数名の継続的な強敵と経験を積んだ元新人を含む | 榎本拓：厚み／長谷川渉：対称性／久保陽：ポージング |

生成後は身体データを基準値から再抽選しない。大会参加者は `hash(local.seed,editionId,cpuId)` と出場予定・経験条件で選ぶ。同じseedと日付なら同じ顔ぶれ。プレイヤーの申込前に開催の参加者予定・直近採点帯を閲覧可能とし、閲覧で乱数を消費しない。各階級4〜6人を目安に予め出場予定を組む。プレイヤーの所属階級に合わせてCPUを軽くしたり増やしたりしない。

CPUは週単位の純粋更新を日次処理から実行。各選手に固定した練習継続率・成長係数・上限・減量／維持／回復のシーズン計画を保存し、1週ずつ上限との差から小さく成長する。短期の調整はCPU自身の周期で変わる。posingは本人の練習量に応じて漸進。疲労を持つCPUも休養で回復する。プレイヤーが負けた後にCPU能力を減らさない。長期は既存CPUの新人卒業・引退と、新規コホートを年1回追加し、記録に登場したCPUは削除しない。新規入場者もプレイヤーに合わせて生成しない。

## ローカル共通採点

プレイヤーと全CPUを必ず同じ `scoreLocal(ContestantSnapshot, LocalRuleSet)` へ通す。Snapshotはbody、posing、asymmetry、systemicFatigue、previousSleepを持つ。現 `scoreBody` のCPU呼出はasymmetry省略＝0、生成CPUの局所疲労も0のため、新ローカル機能は両者に明示入力を用意する。既存officialの結果や `scoreBody` 係数は変更しない。

初版案は筋量30%、バランス20%、仕上がり15%、ポージング25%、当日準備10%。3種のローカル大会で同じ係数を使い、対戦層が難度を作る。内部点はゲーム指標であり公式採点でも身体の医学的評価でもない。

- 筋量：身長で正規化した現 `scoreBody.mass` を利用可能。身長や体重そのものへ加点しない。
- バランス：現balanceとsymmetryを7：3で合成。双方の同じ左右差定義を使う。
- 仕上がり：ローカルは過度な減量を必須にしない固定の広い帯を使う案（例：体脂肪12〜22%を同点、その外は距離に応じて緩く減点）。これは架空の地域大会独自基準。健康適正値・公認基準とは表示しない。疲労はここに重複加算しない。
- ポージング：保存した0〜1技能を0〜100に変換。大会参加ボタンだけで技能値を増やさない。講評後の練習計画が技術を伸ばす。
- 当日準備：局所疲労、全身疲労、前夜の実睡眠から共通の0〜100指標を計算。例として疲労40/30/睡眠30の同一加重を双方に適用し、計算に使った値を結果へ保存。毎回同じ理想状態のCPUにしない。

比較審査を全員実施し総合指標の降順で順位。総合小数値が同点ならposing、balance、readinessの順、すべて同じなら**同順位**として表示する案。プレイヤーやCPUのID順で勝敗を決めない。初版の審査乱数は0とし、再読込・画面表示で結果が変わらない。順位と採点差を両方示す。

## 負けても残る成果と次の行動

結果画面は順位だけを見出しにしない。`初ステージ完了`、`ポージング前回比+1.8`、`筋量指標自己ベスト`、`同じ相手との差が9.2→6.4`、`前夜睡眠と疲労の改善`を、実データに該当するときだけ表示する。PBは種目・採点版別。順位ベストは参加数付きで表示し、2/3と2/12を同じ進歩とは断言しない。

参加記録には日付・大会・クラス・参加人数・順位・全採点・身体写真・当日準備・対戦者IDと内訳を保存。全員の詳細身体を毎回大量に複製せず、プレイヤーと表彰台のbody、全員の採点＋IDを保存する方式がよい。ただし過去全員を3Dで再現する機能を付けるなら当時bodyを別スナップショットとして保存する必要がある。

自己ベストは `total/mass/balance/condition/posing/readiness` の各最大値・初達成resultId・当時日付。集計の正本はresultsで、キャッシュする場合も検証・再構築可能にする。大会ごとの目標を変えてPBの基準を毎回下げない。

リベンジは指定CPUとの対戦履歴から `前回順位・点差→今回順位・点差` を表示。実際に同じ開催・同じクラスで対戦して初めて更新する。相手不出場なら未達のまま残し、次の出場予定へ案内。勝った場合は「初勝利」、差を縮めただけなら「差が縮まった」。相手を選んでもCPU能力・組合せ・結果を変えない。

引退時はlocal出場があれば `ローカル練習会○回、新人大会○回、初ステージの日、自己ベスト、印象に残る再戦` を既存引退本文へ追加する。現在のretireは `progress.results.length===0` なら大会未出場と書くため、**local出場者を大会未出場と呼ばない修正が必要**。公式大会数・ローカル参加数・世界タイトル数は別表示。localに公式TitleやCredentialを発行しない。

## 実装時に衝突する箇所

| 現在の仕組み | 追加時の問題と対応 |
| --- | --- |
| `Series`、`Circuit`、`validateProgress`の固定列挙 | localを混ぜると資格・記録の既存判定が広範囲に変わる。別型・別validatorにする。 |
| `progress.goal`／単一`decision`／`pendingEvent` | localを既存decision.kindへ押し込まない。local.decisionを別保持し、共通の停止調停を設ける。official必要行動→local申込済み必要行動→任意リマインダーの順。片方を了承してもう片方を消さない。 |
| `advance`が前後でlifecycleを呼ぶ | localも日次開始に1回確認し、まとめ送りでも締切・当日を飛ばさない。純粋な閲覧でlocalを初期化・乱数更新しない。未申込全大会で毎回停止せず、目標だけ締切通知。 |
| official当日に移動・checkIn・結果を同日実行 | localも同日checkIn後に1回だけ結果確定。show日後の宙ぶらりん申込はmissed化し永続停止しない。公式日程との重複は申込時に説明、初版は1日1大会に制限。 |
| `simulation.ts`の`onTrip`／練習時間計算 | ローカル2〜6時間を24時間へ入れないと仕事・練習と同時参加できる。初版は競技日に予定を見直す／練習を休む明示。大会参加はsimulation dayを追加で消費しない。 |
| official結果が回復21日を追加 | 練習会へ21日を流用すると隔週再挑戦が止まる。ローカルは軽い当日疲労のみ、翌日休養を提案。回復・違和感の残る選手へ無条件で高負荷を強制しない。 |
| 保存がCareer丸ごと、IDB version1 | optionalの追加だけなら新ストア不要。現saveの単一トランザクションへlocalの費用・結果も同時保存。成功前に画面で結果確定扱いしない。 |
| validatorは未知キーを一般に拒否しない | localが存在するのに無検証で通る危険。`validateCareer`でpresent時のみ`validateLocal`。旧保存にlocalがないのは有効。nullや未来版・NaN・範囲外・参照切れ・二重ID・二重entry結果は拒否。 |
| バージョンが厳密一致 | global official rules版をlocal追加で書き換えない。独立local.rulesVersionで固定。全体content/simulationを変更するなら旧0.2.1を明示受入する移行を追加し、既存career/progress値を書き換えない。 |
| legacyの`progress`自体がoptional | local参加に必要なposing等はenableCareer後に初期化。旧キャリア導入はanchor=currentDay、officialの既存rivals/credentials/results/RNGは保存。 |
| result/body履歴の肥大化 | 20年隔週でも約520回。ローカルresultsは1万件程度を上限とし、1万件超で黙って古い実績を削除しない。CPU個人履歴も結果ID参照を基本にして二重全履歴コピーを防ぐ。 |

`Career.local`の導入タイミングは新規生成またはユーザーが既存キャリアを開いた際の明示的な移行保存。移行前の任意通知だけで日次シミュレーションや保存のrngを消費しない。既存official RNGと共有せず、固定seedからlocal専用列を導出する。

## 必須の検証案

1. 6プロフィールとも通常生成で14日目の練習会が表示され、同一状態なら同じ採点。最初の4週間で新人開催もある。勝利の保証はしない。
2. 初回敗北後2週間以内に再挑戦先が存在。初回未申込・締切超過も次開催を表示。localの優勝／敗北で公式資格・世界タイトルは増えない。
3. 同じローカルseed・dayでプレイヤー身体／profileId／敗北数だけ変えてもCPUの身体・予定・成長は一致。
4. 同じsnapshotをplayerとCPUへ入れると全項目が一致。疲労・睡眠の同じ差が同じ点差になる。BMIや名前だけで点を変えない。
5. day送り×7と週間送りの結果・CPU状態・締切停止が一致。再読込、連打、二重checkIn／結果確定で費用・疲労・記録を重複しない。
6. 新人の経験4→5回、複数申込、欠場、同日officialとの重複、体重70／85kgちょうど、階級統合、参加不足を確認。
7. localなし旧保存、localあり保存・再読込・export/import・重複インポート、保存容量エラーを検証。旧official結果・資格・titlesは完全一致。保存失敗では旧所持金と旧localを保持。
8. 入賞なしで3回出場→PBと対戦差が残る→引退→記録室で再表示。引退後はlocalにも申込・進行・結果追加不可。即引退と最終シーズン引退の未完了local申込を閉じる。

本提案はsrcを変更しない調査・コンテンツ案。優勝必須の解放、負け続けた選手への点数救済、CPU追随弱体化、profileIdによる成長分岐は採用しない。
